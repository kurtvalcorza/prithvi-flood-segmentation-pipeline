#### Description

`ibm-nasa-geospatial/Prithvi-EO-2.0-300M-TL-Sen1Floods11` at revision `91ce9d38086a80b078a192b374df758b8855b732` is the upstream authors' flood-mapping fine-tune of Prithvi-EO-2.0 (Szwarcman et al., 2024), NASA and IBM's foundation model for Harmonized Landsat Sentinel-2 imagery: a ViT-L masked autoencoder (24 blocks, embedding dimension 1024, 16 × 16 patches, six input bands) pretrained on 4.2 M global multispectral samples, in its `TL` variant whose encoder also carries temporal and location embeddings. The checkpoint packaged here, `Prithvi-EO-V2-300M-TL-Sen1Floods11.pt` (1,276,843,350 bytes, SHA-256 `76eed77d…`), is the `terratorch` `EncoderDecoderFactory` model that fine-tuning produced — the encoder (296 tensors), a `SelectIndices` → `ReshapeTokensToImage` → `LearnedInterpolateToPyramidal` neck over encoder depths 5, 11, 17 and 23 (11 tensors), a UPerNet decoder with 256 channels (72 tensors) and a two-class head with dropout 0.1 (2 tensors): 318,968,580 parameters in float32, trained with cross-entropy on the 446 hand-labelled 512 × 512 chips of Sen1Floods11 (blue, green, red, narrow NIR, SWIR 1 and SWIR 2) for 41 epochs (630 steps) without metadata — the temporal and location embeddings receive no coordinates, in training and here. At inference the model standardises the six bands with the datamodule's statistics, encodes the chip, builds a feature pyramid from four depths, decodes it and returns two logits per pixel at input resolution; `argmax` gives the mask.

What this repository adds is the `PrithviFloodPipeline` class in `src/prithvi_flood_segmentation_pipeline/pipeline.py`: manifest verification of the 7-file Hub snapshot before any model library is imported (`verify_snapshot`, which also checks the converted file against its pinned digest when present), fresh-clone staging at the pinned revision (`stage_missing_files`), a **static audit of the pickle** that lists every global it would import with `pickletools` and refuses anything outside the allow-list (`audit_pickle`, digest pinned), a **one-time conversion** through torch's weights-only unpickler into a strictly loaded model whose state dict is saved as safetensors (`convert_model`), model construction from the installed `terratorch` package with `backbone_pretrained=False` (`build_model`), chip validation with named ceilings (`validate_inputs`, `validate_dataset`), segmentation with softmax scores and class fractions (`predict`), pixel-pooled IoU / F1 / precision / recall against the no-water baseline (`evaluate`), bounded fine-tuning of the neck, decoder and head — optionally also the last encoder block — with frozen BatchNorm statistics (`adapt`), and a safetensors adapter artifact that is digest-verified and scope-checked before deserialization (`save_artifact`, `from_artifact`). `samples.py` fetches 44 digest-pinned chips from the public Sen1Floods11 bucket with the official roles and reads/writes GeoTIFF pairs for BYOD with `tifffile` (no rasterio, no georeferencing); `metrics.py` holds the confusion-matrix metrics and the baseline.

Two things about this profile are stated rather than hidden. **The model already trained on the tutorial's dataset** — the 44 chips are drawn from the official Sen1Floods11 splits — so the frozen numbers are in-distribution and the bounded adaptation has little to learn from 24 chips; the card reports the paired held-out numbers as observations and claims no improvement. **Georeferencing and metadata are not used**: chips are read as pixel arrays, the `TL` embeddings receive no coordinates (as in the upstream fine-tune, whose datamodule ran with `use_metadata: false`), and scenes larger than a chip are not tiled.

#### Intended Use and Limitations

###### Primary Intended Uses

Two tasks are exposed. **Flood-extent segmentation:** input is a 512 × 512 chip of six surface-reflectance bands (blue, green, red, narrow NIR, SWIR 1, SWIR 2; values in [0, 1] or × 10 000, no-data 0 or −9999) or a GeoTIFF from which they are read (13-band Sentinel-2 L1C files are reduced to the six bands as upstream's inference script does); output is a per-pixel mask (0 = no water, 1 = water), the two softmax scores per pixel and the water fraction. **Adaptation to labelled chips:** given at least four chips with masks (0 / 1 / −1 for no data), the pipeline fine-tunes the neck, decoder and head (optionally also the last encoder block) with a small learning rate and validation-loss epoch selection, predicts with the adapted model and exports the changed tensors as a 60 MB adapter. Envisioned application domains are flood-extent mapping from optical satellite chips in research and public-sector workflows — rapid mapping after a flood event, building training data for a regional model, teaching and evaluating foundation-model fine-tuning for Earth observation; and prototyping a segmentation service whose skill is then measured against the operator's own labels. In a larger system the pipeline is a single-chip segmenter and an adaptation baseline whose masks feed an analyst's review or a downstream tiling/mosaicking step; it is not a scene-level flood product, a change-detection system or a hydrological model.

###### Primary Intended Users

Intended users are Earth-observation scientists, disaster-response and GIS analysts, and machine-learning engineers who work with Sentinel-2 or HLS chips, in research, public service or the DIMER model workbench. The pipeline assumes its users understand that the model learned six specific bands at a specific scaling and that band order and reflectance units are part of the contract; that a hand label carries its own uncertainty at water edges and under cloud; that neighbouring chips are near-duplicates, so splits must be by scene or event; that the no-water baseline is the number to read first on chips with little water; and that a 12-chip evaluation is a sanity check, not a measurement of skill.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline segments water in single-date six-band optical chips and fine-tunes the decoder side of the model. It does not use Sentinel-1 SAR (the other half of Sen1Floods11), temporal stacks, or the location/temporal embeddings; it does not tile scenes, mask clouds, correct atmosphere, or estimate flood depth or duration; and it does not reproduce the published benchmark scores.
2. **Input boundary:** chips are exactly 512 × 512 pixels with exactly six bands in the Prithvi order; values must be finite reflectance in [−0.5, 2] after scaling (values above 1 are divided by 10 000); labels hold only 0, 1 and −1; datasets hold 4..2,000 records with at least one water pixel. Other sizes, band sets, radiometric products (digital numbers, radiance), or label vocabularies are not inputs.
3. **Decision boundary:** not for autonomous action on a mask — evacuation, aid allocation, insurance or damage assessment, infrastructure decisions — without verification against the deployment's own reference over a representative set of scenes and an analyst's review. A mask from this pipeline is an experiment output, not a flood product.
4. **Provenance boundary:** not for settings that require the upstream serialized checkpoint to be executed as-is, or that forbid any one-time unpickling of a third-party checkpoint even through a restricted loader after a static audit; the trust boundary is documented under *Mitigations* and in `docs/WEIGHTS.md`.

#### Factors

###### Groups

The pipeline's inputs are satellite reflectance chips, not records about people, so age, gender, skin type and socioeconomic status are not attributes of any input and no demographic evaluation applies. The relevant groups are geographic and physical: flood events differ by region (Sen1Floods11 spans eleven events across Bolivia, Ghana, India, the Mekong, Nigeria, Pakistan, Paraguay, Somalia, Spain, Sri Lanka and the USA), by land cover (open water reads differently against bare soil, vegetation, urban surfaces and wet sand), by water turbidity and depth, by sun angle and by cloud and shadow. Upstream reports one pooled score; this repository measures 12 test chips from seven regions and 8 validation chips from six, pooled over pixels, and reports no per-region numbers — whose floods are mapped well is therefore unmeasured here, and a deployment serving a region should measure it there. Communities whose floods are under-represented in the training events, or whose landscapes resemble water spectrally, bear the error.

###### Instrumentation

The instrument is Sentinel-2's MultiSpectral Instrument: the chips are Level-1C top-of-atmosphere reflectance at 10–20 m resampled to 10 m, encoded as integer reflectance × 10 000 with 0 as no-data, from which six bands are taken (B2, B3, B4, B8A, B11, B12). The labels were drawn by hand from the same imagery (with Sentinel-1 at hand) by the Sen1Floods11 authors, and −1 marks cloud and no-data. Instrument and processing defects reach the model as feature error — a different processing baseline, a different atmospheric state, cloud shadow, sun glint, or a band-order mistake all shift the six values the model reads, and the pipeline detects none of them: validation checks shapes and ranges, not radiometry. The model's own instrument is its patching, 16 × 16 pixels per token, so a 160 m square is one token and narrow channels are sub-token.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `torchvision==0.29.0`, `terratorch==1.2.13` (which brings torchgeo, lightning, timm, segmentation-models-pytorch, albumentations, rasterio and others as its own dependencies; the pipeline imports only `terratorch.models.EncoderDecoderFactory`), `tifffile==2026.9.15`, `numpy==2.5.3`, `safetensors==0.8.0`, `huggingface-hub==1.32.0` (`pyproject.toml`). The model is float32 as shipped and runs in float16 autocast on CUDA (`device` defaults to CUDA when visible, CPU otherwise); the recorded run is under *Runtime* (load 22–27 s, 12 chips scored in 1.3 s, a 48-step adaptation in 9.4 s, 2.2 GB of GPU memory on an RTX 5070 Ti laptop GPU). CPU execution works but is slow (tens of seconds per chip). Data environment: the model assumes Sentinel-2-like reflectance of the six bands at the datamodule's statistics, single-date chips of flood events similar to Sen1Floods11's; it degrades, without any error, on other sensors, other radiometric products, snow and ice, wet soil and shadow, all of which can read as water.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.segmentation_metrics` names them, over the pooled labelled pixels of every chip scored (pixels labelled −1 excluded): `iou` per class (`no water`, `water`), `mean_iou`, `accuracy`, and for the positive class `precision`, `recall` and `f1`, plus the confusion matrix, the labelled-pixel count and the positive fraction. Three comparison points are read together: the **no-water baseline** (`majority_baseline`, every pixel predicted as land — its accuracy equals the land fraction and its water IoU is 0), the **frozen model**, and the **adapted model**. IoU and F1 of the water class are the headline because accuracy is dominated by land on most chips; precision and recall are kept apart because the frozen model's error is asymmetric on this sample (recall 0.79, precision 0.70 on the test chips: it over-predicts water). Every number in this repository is sample-sanity evidence on 12 test and 8 validation chips from one seeded run with no dispersion estimate; no number from the Prithvi-EO-2.0 paper or the Sen1Floods11 benchmark is reproduced or claimed.

###### Decision thresholds

The default decision rule is an `argmax` over the two per-pixel logits, equivalent to a 0.5 threshold on the water softmax score; `predict` returns both scores so a deployment can apply its own threshold, and the pipeline sets none. The limits fixed during development are input-contract limits, not decision thresholds — the 512 × 512 chip size, the six-band count, the reflectance range after scaling, the label vocabulary, the 4..2,000 record range — chosen so that a rejection names a real defect and an acceptance never means "radiometrically correct". An operator who needs a threshold (a minimum water score before a pixel counts as flooded, or a minimum flooded fraction before a chip is flagged) must set it from verification against their own labels, weighing the cost of a missed flooded pixel against a false one, and own it. `adapt` selects the epoch with the lowest validation loss, which is the only selection this repository performs.

###### Approaches to uncertainty and variability

Reported metrics come from one seeded run on **pixel-pooled** held-out chips — 12 test chips from the official test split for the numbers, 8 validation chips for epoch selection only — with no cross-validation, bootstrap, ensemble or repeated-run averaging, and no dispersion is reported: with 12 chips of one dataset, any interval would be dominated by which chips were drawn, and chips with much water dominate the pooled counts. A caller who needs one evaluates many chips across events and reports per-scene distributions, and owns that design. Sources of run-to-run variability: the flip augmentation and shuffling are seeded (`numpy` generator), initialisation is the pinned checkpoint, and BatchNorm statistics are frozen; float16 autocast, non-deterministic GPU kernels and the gradient scaler are not controlled, so a re-run can differ in the last decimals of the adapted numbers while the frozen numbers are reproducible. The softmax scores are the model's outputs and are **not calibrated probabilities**; no per-pixel uncertainty beyond them is produced, and calibration against the operator's labels is theirs to do.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of all 7 manifest entries before any load, additionally asserts the checkpoint's digest against the package constant, and raises on the first mismatch (tests flip bytes, change the identity and delete a file and assert each raises). `stage_missing_files()` fetches only manifest-listed files absent on disk, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. `.gitattributes` carries `weights/** -text`.
2. **Executable serialization handled explicitly (asset spec §11.2):** the pickle is not loaded by the runtime path. `audit_pickle` lists every global it would import with `pickletools` (`collections.OrderedDict`, `torch._utils._rebuild_tensor_v2`, `torch.FloatStorage`, `torch.LongStorage`) and refuses anything else; the audit digest is pinned. `convert_model` runs size → digest → audit before `torch.load(weights_only=True)` (torch's restricted unpickler, which cannot construct arbitrary objects), requires a `state_dict` of tensors whose every key carries the Lightning `model.` prefix, and loads it with `strict=True` into `EncoderDecoderFactory().build_model(...)` with `backbone_pretrained=False`; the model's state dict is re-saved as safetensors. Tests craft an archive with `os.system` and a plain pickle of a `complex` and assert each is refused before anything is unpickled.
3. **Deterministic, digest-pinned serving file:** `verify_converted` checks size and SHA-256 against `CONVERTED_SHA256` / `CONVERTED_BYTES` (reproduced by the build, the smoke runs and the executed notebook); the model loads with `strict=True` and a parameter-count check. With `require_source=False` (the DIMER-hosted case) the converted file alone is accepted, still digest-verified.
4. **Data integrity:** every Sen1Floods11 object the tutorial fetches (88 objects) has its byte size and SHA-256 pinned in `SAMPLE_RECORDS`; `fetch_object` refuses a mismatch before decoding, and roles come from the official split files. `check_split_disjoint` refuses a chip present in two splits.
5. **Artifact integrity and scope:** the adapter is safetensors, not a pickle. `load_artifact` validates the manifest **before** deserialising anything: the artifact format and `format_version`, the recorded base model id, revision and converted-base digest, exactly one weights entry named `adapter.safetensors` that resolves inside the artifact directory, an `adapter.trainable` that is exactly `decoder` or `decoder+last_block`, and a tensor list equal to the exact set that scope may change on this model; the safetensors keys must then equal that set and every shape must match. The weights file's SHA-256 is checked against the adjacent manifest — it detects corruption or drift of the file relative to that manifest, not authenticity: an actor who can replace both files can make them agree.
6. **Input integrity:** `predict`, `evaluate`, `adapt`, `validate_inputs` and `validate_dataset` route through one checker, so their acceptance criteria cannot diverge; it rejects missing keys, wrong shapes, band counts and chip sizes, non-finite values, out-of-range reflectance after scaling, label values outside {−1, 0, 1}, duplicate ids and datasets without a water pixel; no-data is replaced by 0 as upstream does and values above 1 are scaled by 10⁻⁴, both reported.
7. **Training discipline:** only the declared scope receives gradients (the encoder stores no graph), BatchNorm running statistics stay frozen (batches of two chips would corrupt them), the learning rate defaults to 10⁻⁵, gradients are clipped at norm 1, the epoch is selected by validation loss with the frozen model as epoch 0, and `adapt` is transactional — any failure restores the pre-adaptation tensors, re-freezes the model and clears the adapter.
8. **Import boundary:** verification, the static audit and validation run before `torch`, `terratorch`, `timm`, `lightning`, `safetensors` or `huggingface_hub` are imported (DIMER RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library, and an AST check fails if any of them is imported at module level.
9. **Honest scope:** validation is labelled structural, the sample is labelled in-distribution, the softmax scores are labelled uncalibrated, the baseline is printed before any model number, the notebook asserts only what the procedure guarantees, and no upstream benchmark is claimed.

Not implemented, and therefore not claimed: no tiling of larger scenes, no cloud masking, no use of the temporal/location embeddings, no full-encoder fine-tuning, no calibration, no per-region evaluation, and no measurement beyond the 44-chip sample.

###### Risks and harms

1. **A conversion can be subtly wrong:** the evidence is the strict key-and-shape match against the rebuilt architecture and sane predictions on the upstream example chips, under one `terratorch` version. A future package version that changed a block's semantics while keeping its parameter names would load strictly and silently compute something else; the exact pin is the control.
2. **A pickle audit is an allow-list, not a proof:** the static audit bounds what the unpickler can name; torch's weights-only unpickler bounds what it can construct. The digest pins tie the audited bytes to the loaded bytes, and the unpickle happens once, in the operator's environment.
3. **Spectral confusion:** cloud shadow, wet soil, dark vegetation, snow and burnt areas can read as water and are predicted with the same silent confidence; the operator bears the false alarms and the data subject — communities on the map — bears the misses.
4. **In-distribution optimism:** the sample chips come from the events the model trained on; a reader who carries the frozen numbers to a new region or sensor draws an unsupported conclusion.
5. **Near-duplicate leakage:** neighbouring chips of one event are near-duplicates; a split over shuffled chips makes memorisation look like skill. Neither the model nor this repository can detect a leaking split the operator builds.
6. **Catastrophic forgetting and drift:** fine-tuning the decoder on a few chips of one event can degrade other events; validation selection guards against the worst case on the validation chips only.
7. **Band-order and unit mistakes:** a chip with the bands in another order or in radiance units is segmented without complaint; validation catches shapes and ranges, not meaning.
8. **Automation bias and proprietary data:** a clean-looking mask invites acting on it without review, and the realistic confidentiality failure is licensed imagery or an unreleased assessment uploaded to a cloud notebook — inference is local, but the runtime may not be the operator's.

###### Use cases

The model must not be used to direct evacuation, aid, insurance, damage assessment or infrastructure decisions, or to produce any map presented as an operational flood product, without verification against the deployment's own labels over a representative set of scenes and a qualified analyst's review; it must not be used as evidence about Prithvi-EO-2.0's benchmark skill, which this repository does not measure; it must not be used to load or execute the upstream pickle in any way other than the audited, digest-verified, one-time conversion this repository performs; it must not be used to redistribute Sen1Floods11 chips without the CC BY 4.0 attribution; and it must not be used in any way that breaches the Apache-2.0 terms of the upstream weights or the DIMER deployment terms.

## Input/output contract

- `PrithviFloodPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False, require_source=True, report=None)`: stages and verifies the snapshot, audits and converts the checkpoint when the safetensors file is absent (reporting through `report`), builds the architecture from `terratorch` and loads the safetensors strictly. `require_source=False` accepts the digest-verified converted file without the checkpoint.
- `predict(records, *, batch_size=4) -> dict` with `model` (id, revision, key, `adapted`), `classes`, `decision_rule`, `predictions` (per record: `id`, `mask` (H, W) uint8, `scores` (2, H, W) float32, `class_fraction`), `seconds`.
- `evaluate(records, *, batch_size=4) -> dict`: `n_records`, `metric`, `model` (`iou` per class, `mean_iou`, `accuracy`, `precision`, `recall`, `f1`, `confusion`, `labelled_pixels`, `positive_fraction`), `baseline_no_water` (the same fields), `adapted`, `seconds`.
- `adapt(train, val=None, *, epochs=4, lr=1e-5, batch_size=2, trainable="decoder", seed=0, progress=None) -> dict`: bounded AdamW fine-tuning; returns the trainable set and counts, hyperparameters, `best_epoch`, per-epoch `history` (epoch 0 = the frozen model, each with `train_loss`, `val_loss` and the validation metrics) and `seconds`. `trainable="decoder+last_block"` also unfreezes encoder block 23.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` (the trained tensors) + `manifest.json` (format, base model id/revision/key and converted digest, adaptation record, history, tensor names, file size and SHA-256); `from_artifact(...)` / `load_artifact(...)` verify all of that before deserialising.
- `validate_inputs(record) -> dict` (`id`, `shape`, `reflectance_range`, `has_label`, `label_fraction`, `ignored_pixels`) and `validate_dataset(records, *, min_records=4, max_records=2000, require_labels=True) -> dict` (normalised `records`, counts, `class_pixel_fraction`, `ignored_pixels`, `reflectance_range`, `digest`) raise exactly what the execution path would raise; `check_record` returns one normalised record. `read_chip(path, band_indices=None)` / `read_mask(path)` read GeoTIFFs with `tifffile`; `fetch_sample_dataset(cache_dir=None)` / `fetch_corpus` / `fetch_object` are the pinned-data primitives; `load_byod_dataset(path)`, `write_sample_pair`, `write_dataset_csv` the BYOD I/O; `split_dataset`, `check_split_disjoint`, `dataset_manifest` the split helpers; `segmentation_metrics`, `confusion_matrix`, `metrics_from_confusion`, `majority_baseline` the metrics.
- `audit_pickle(path, allowed=…)`, `convert_model(path=None)`, `verify_converted(path=None)` and `build_model()` are the serialization primitives.
- Constants: `BANDS` (6), `S2_L1C_BAND_INDICES = (1, 2, 3, 8, 11, 12)`, `MEANS`, `STDS`, `CONSTANT_SCALE = 1e-4`, `IMAGE_SIZE = 512`, `NUM_CLASSES = 2`, `CLASS_NAMES = ("no water", "water")`, `IGNORE_INDEX = -1`, `MIN_RECORDS = 4`, `MAX_RECORDS = 2000`, `PARAMETER_COUNT = 318968580`, `STATE_TENSORS = 381`, `ADAPTATION_MODES = ("decoder", "decoder+last_block")`, `ARTIFACT_FORMAT = "org.valcorza.prithvi-flood-segmentation.adapter.v1"`.

## DIMER deployment notes

| Field | Status |
|---|---|
| **DIMER status** | **Planned / conditional** — the `.pt` asset-format and deserialization-trust review DIMER requires is what this repository implements; the review's acceptance is the maintainer's call |
| Licence | Apache-2.0 (weights, the upstream Prithvi-EO-2.0 code, TerraTorch, and this repository's code) — use, modification, redistribution and commercial use permitted with the licence and notices preserved |
| Weights | Would be redistributed converted, not unmodified: the served artifact is the deterministic safetensors derived from the pinned checkpoint, with both identities recorded (asset spec §11.2); this repository redistributes neither |
| Remote code | **Not required** — no Hub-hosted module is imported; the model class comes from `terratorch==1.2.13` on PyPI |
| Executable serialization | One pickle, unpickled **once** at conversion through torch's weights-only loader after a digest check and a static audit; a DIMER profile should carry the safetensors file and never the `.pt` |
| Runtime | `terratorch==1.2.13` + `torch==2.14.0` + `torchvision` + `tifffile`; float16 autocast on CUDA; a GPU is advisable (a chip takes tens of seconds on CPU); the `terratorch` install is heavy (torchgeo, lightning, rasterio and their dependencies) |
| Upload format | `prithvi-eo-2.0-300m-tl-sen1floods11.safetensors` (1,276,749,320 bytes, SHA-256 `65e4377f…`); **the `.pt` file must not be uploaded** |
| Input contract | 512 × 512 chips of six bands (blue, green, red, narrow NIR, SWIR 1, SWIR 2) as arrays or GeoTIFFs; reflectance in [0, 1] or × 10 000; labels 0 / 1 / −1 for adaptation |
| Sample data | fetched at run time from the public Sen1Floods11 bucket (CC BY 4.0), never vendored |

**One thing is open, and it is neither the licence nor the code:** whether a one-time unpickle through torch's weights-only loader, after a static audit with a pinned digest — in the build and in the tutorial runtime, where the notebook converts what it downloads — meets the DIMER bar, or whether DIMER should host only the safetensors converted and verified once by the maintainer. The served artifact is the same file either way.
